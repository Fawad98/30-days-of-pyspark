User Defined Functions
Power Tool — Handle With Care

Python UDFs vs Pandas UDFs — and why the wrong choice tanks performance

// What is a UDF?

A UDF (User Defined Function) lets you apply custom Python logic to a DataFrame column when Spark's built-in functions aren't enough. They're powerful — but come with a real performance cost. Knowing which type to use and when to avoid them entirely separates good engineers from great ones.

// 3 Ways to Define Custom Logic — Ranked by Performance
Python UDF
⚠ Slowest

Serializes each row to Python, processes it, returns to JVM. Row-by-row. No Spark optimizations. Use only as last resort.

Pandas UDF
✦ Fast

Uses Apache Arrow for batch transfer. Processes chunks as Pandas Series. 10–100x faster than Python UDFs.

Built-in F.*
★ Always First

Pure JVM execution. Catalyst optimizer can see and optimize them. Zero Python overhead. Always prefer these.

// Python UDF vs Pandas UDF in Action
day09_udfs.py 
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import StringType, DoubleType
from pyspark.sql.functions import pandas_udf
import pandas as pd

spark = SparkSession.builder.appName("Day09").getOrCreate()

data = [("alice smith", 95000.0), ("bob jones", 72000.0),
        ("charlie brown", 88000.0), ("diana prince", 81000.0)]
df = spark.createDataFrame(data, ["name", "salary"])

# ════════════════════════════════════════════════════
# ① PYTHON UDF — row by row, slow, avoid in production
# ════════════════════════════════════════════════════
@F.udf(StringType())
def title_case(name: str) -> str:
    if name is None:
        return None
    return " ".join(w.capitalize() for w in name.split())

df = df.withColumn("name_titled", title_case(F.col("name")))

# ════════════════════════════════════════════════════
# ② PANDAS UDF — batch processing via Arrow, much faster
# ════════════════════════════════════════════════════
@pandas_udf(DoubleType())
def apply_tax(salary: pd.Series) -> pd.Series:
    # Entire column arrives as a Pandas Series — vectorized!
    return salary.apply(lambda s: s * 0.75 if s > 80000 else s * 0.85)

df = df.withColumn("net_salary", apply_tax(F.col("salary")))

# ════════════════════════════════════════════════════
# ③ BUILT-IN — always try this FIRST (fastest by far)
# ════════════════════════════════════════════════════
df = df.withColumn("name_titled_native",
    F.initcap(F.col("name"))  # Same result, zero Python overhead!
)

# Register UDF for Spark SQL
spark.udf.register("title_case", title_case)
spark.sql("SELECT title_case(name), salary FROM employees")

df.show()
spark.stop()
✦ The Golden Rule: Before writing any UDF, spend 5 minutes checking if pyspark.sql.functions already has what you need. In the example above, F.initcap() does exactly what the Python UDF does — with zero Python overhead and full Catalyst optimization.
⚠️ Python UDF performance cost: Each row is serialized from JVM → Python → JVM. On 1 billion rows, that's 3 billion serialization operations. Spark's Catalyst optimizer also can't see inside a UDF — it treats it as a black box and can't optimize around it. Use Pandas UDFs when custom Python logic is unavoidable.
// Key Takeaways
  • Always check pyspark.sql.functions first — built-ins run on the JVM and are always faster.
  • If you must use a UDF, prefer pandas_udf — it uses Apache Arrow for batch transfer, not row-by-row serialization.
  • Python UDFs are black boxes to Spark — the Catalyst optimizer cannot see inside or optimize around them.
  • Always handle None explicitly inside UDFs — null inputs don't raise errors, they silently return null.
  • Register UDFs with spark.udf.register() to use them in Spark SQL queries.
